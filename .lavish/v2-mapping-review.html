#1 of 20 1.15 Internal linking structure

1.15 internal-linking and 10.11 internal-cross-linking measure the same link graph. The evidence review found BOTH falsy the same way (nav/footer links make them near-unconditional passes) and both need the identical fix: count only in-content links.

1.15 Internal linking structure (content-discoverability/internal-linking)

Code today: For every scanned page, counts all a[href] whose resolved hostname equals or is a subdomain of ctx.domain. Fails only if every page has zero such links, warns if some pages have zero, otherwise passes and reports an average that is never used as a threshold.

Claims: A strong internal linking structure helps AI crawlers discover and understand the relationships between your pages.

Evidence: grade A; disposition: keep - fix required (review_verdict fix, severity medium). Verdict: signal is grade-A real (non-JS-executing AI crawlers depend on the <a href> link graph) but the code counts same-page #fragments and nav/footer chrome as internal links and only fails at literally zero, so it passes ~100% of real sites and never enforces the 3-5 links per page its own guidance prescribes.

10.11 Internal cross-linking (generative-engine/internal-cross-linking)

Code today: Uses extractInternalLinks over the whole document for each page, drops links whose pathname equals the page's own, and counts a page as well-linked at >=2 remaining links. Passes if every page qualifies, warns if some do, fails if none do. Nav, header and footer links count the same as body links.

Claims: AI engines use internal link structure to build topic clusters and assess site authority; pages without cross-links are treated as isolated content.

Evidence: grade unrated; disposition: keep - fix required (review_verdict fix, severity high). Verdict: falsy as implemented - global nav and footer alone put every page far above the 2-link threshold, making this a near-unconditional PASS running at high priority that consumes a report slot while distinguishing nothing; nothing in the code measures the contextual in-content linking the description claims.

Why the recommendation: Two audits, one measurement, one shared fix — keeping both means maintaining the same logic twice and double-counting one signal.

#3 of 20 1.19 Fast page load

fast-page-load (all pages, fail >1800ms any page, warn >800ms mean) and fast-response-time (homepage only, hard 800ms cliff) both read the same ttfbMs number. Both dossiers demand the same fix: median of repeated samples, sane bands.

1.19 Fast page load (content-discoverability/fast-page-load)

Code today: Reads page.fetchResult.ttfbMs for each scanned page. Fails if any single page exceeds 1800ms, warns if the mean across pages exceeds 800ms, otherwise passes. Uses one unrepeated sample per page.

Claims: AI crawlers have limited time budgets, so fast TTFB lets them fetch more of your pages per session.

Evidence: grade B; disposition: keep - fix required (review_verdict fix, severity medium). Verdict: the concern is legitimate but the measurement is a single cold sample taken while the scanner fetches the same origin many-ways in parallel (the audit creates the latency it reports) and ttfbMs also folds in DNS and TLS, so verdicts vary run to run.

8.12 Fast response time (technical-readiness/fast-response-time)

Code today: Homepage only. Reads pages[0].fetchResult.ttfbMs and passes below a hard 800ms cliff, fails at or above it at high priority with score 0; fails at critical priority if the fetch errored or returned status 0. Declared ternary but there is no warn band.

Claims: AI crawlers like GPTBot and ClaudeBot enforce 2-3 second per-page timeouts, and slow TTFB reduces pages crawled per session.

Evidence: grade B; disposition: keep - fix required (review_verdict fix, severity high). Verdict: real signal, but a hard 800ms cliff on a single cold measurement that includes DNS, TCP and TLS setup (routinely 300-600ms before the origin does any work) makes the verdict close to a coin flip, and the audit's own copy citing a 2-3 second crawler timeout disagrees with its threshold by a factor of three.

Why the recommendation: One TTFB signal, two audits, two arbitrary thresholds — the rewritten median-based audit covers both.
